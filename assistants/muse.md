# Meta Muse Bot adapter

- Free. A recommended addition, like Grok Bot: a bot with its own computer that the owner hands whole jobs to, from any device. Setting it up runs **Add a bot** in the setup skill. Muse has no template sharing, so its standing instructions go in SOUL.md as below.
- **Connect your hub:** tell Muse "Connect my Notion" and approve access to your guava-hub. Start with just the hub, not your whole workspace.
- Muse doesn't let you upload your own skills, so don't install them as files. Keep the skills in the hub and have Muse read the matching one from there when a task needs it.
- **Add the standing instructions:** click the bot's avatar, open the fingerprint tab (the last icon), and open the **SOUL** card. ![Muse profile with the fingerprint tab and the SOUL card](https://raw.githubusercontent.com/romeodiaz/guava-stack/main/assets/setup/muse-fingerprint.png) ![SOUL.md open, with the lines starting "Load my guava-hub in Notion first." at the end](https://raw.githubusercontent.com/romeodiaz/guava-stack/main/assets/setup/muse-soul.png) Add these lines at the end, then save. Add to what's there; never replace or delete anything. The routing line reads the models from guava-stack settings, so swapping one there needs no change here:
  ```
  Load my guava-hub in Notion first. Before any substantive task, read its context, rules and skills and treat them as the source of truth.
  Tasks: log work in the hub's tasks database when it changes something (a hub page, a repo, a memory, anything outside) or gets handed to another model or session; skip questions and quick lookups. When the work starts, add a task: Request in my words, Goal (the real goal, what done looks like, what would count as failure), Assistant, and Status Running. When it ends, set Status (Done, Done with concerns, Blocked or Needs you), Touched and Links, with hand-off notes in the task's page. Put its ID (such as TASK-12) at the start of commit subjects and PR titles, in hand-offs, and after the `Decided:` date in any memory it decided. A hub edit goes on its task, with Touched set to Hub, never on the old changelog page, which stays only as an archive. No passwords, keys, other people's personal details or clients' confidential information in tasks.
  Model routing: use the head-chef, line-cook and computer-use slots in my guava-stack settings, re-reading their model lines right before each hand-off, using each model slot's CLI and named effort (`claude -p --effort <effort> "<task>" < /dev/null` for Claude Code, `codex exec -c model_reasoning_effort=<effort> --skip-git-repo-check "<task>" < /dev/null` for Codex): the head-chef for orchestration, research, planning, brainstorming, copywriting, validation, review, verification, fuzzy and hard problems; the line-cook for bulk execution, coding, sub-agent tasks, worker threads and long-running jobs; quick replies and connector lookups stay with you; browser tasks use browser tools first, in the browser where the owner is already signed in; apps outside the browser go to the computer-use slot named in guava-stack settings (re-read its model line before each hand-off), or to your own computer tools when it names them; never add a service_tier flag for computer-use; if a hand-off fails, follow Repair in guava-router/skills/guava-router/SKILL.md from github.com/romeodiaz/guava-stack and retry once; if it still fails, do the task yourself and say so; when a skill defines how it runs, follow the skill and use routing only for work it leaves open. Run routed work through the CLI without being asked, and mention which one you used.
  When I say "update" or "uninstall" with "guava-stack", "guava-hub", "guava-router" or "founder-mode", follow the Update or Uninstall step in that piece's skill from github.com/romeodiaz/guava-stack: guava-hub/skills/guava-hub/SKILL.md (it also handles "guava-stack"), guava-router/skills/guava-router/SKILL.md or founder-mode/skills/founder-mode/SKILL.md. These always mean the published guava-stack in that repo, never a plan or notes of your own, so read the step there before doing anything.
  Save the tools my business uses and the tasks I do again and again to my Notion Memory, as the Tech stack and Workflows memories. When I say "run my free AI assessment", follow guava-hub/skills/free-ai-assessment/SKILL.md from github.com/romeodiaz/guava-stack.
  When I ask to change my setup (for example "change my setup", "apply my guava-stack settings" or "check for newer models"), follow the Change your setup step in guava-hub/skills/guava-hub/SKILL.md from github.com/romeodiaz/guava-stack.
  ```
  A chat that's already open keeps the SOUL.md it started with, so changes apply in a new chat: tell the owner to start one after any SOUL.md edit, and check from there.
  Leave IDENTITY.md alone. Use MEMORY.md only for facts about the owner, never for passwords, keys or other secrets.
- **Verify:** start a new chat and ask "Write a short intro about my business." It passes if the intro uses details from the hub.
- **Run the CLI steps and model router in Muse's own terminal.** Muse can install Claude Code with npm and usually has Codex already; follow step 2 of the Model Router setup in guava-router (it checks and skips what's installed). For sign-in, the owner opens the link and signs in with their own account, then pastes any code straight into Muse, never anywhere else. When Muse asks to share information with anthropic.com or openai.com, choose Allow once, not Always allow.
- Muse's computer image ships its own older Codex in `/opt/hatch-image/bin`, ahead of npm's on PATH, so a plain `codex` can stay old after an update. Run Codex by the full path of the updated one, `$(npm prefix -g)/bin/codex`, as **Repair** in the guava-router skill says.
- Muse asks before important actions like sending email. Keep those approvals on.
