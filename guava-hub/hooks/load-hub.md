Guava Stack (guava-hub plugin): before substantive work, load the owner's guava-hub in Notion: the rules page, the context page (which starts with guava-stack settings) and enabled skills. Treat the hub as the source of truth. A rules skill marked for one kind of work, such as "(coding)", applies only to that work. Full steps: <skill>/SKILL.md.
- Work from the local copy in `~/.guava-hub`, whose context, rules and skill list follow below. Read a skill's file in `skills/` only when a task needs it.
  - At the start of each task and before each hand-off, `find ~/.guava-hub/sync.md -mmin -15` prints nothing when the copy is due. Then refresh it: one Notion search with `page_url` set to the guava-hub ID in `sync.md`, query "guava-hub" and page_size 50 lists every hub page with its last-edited time. Fetch only pages edited at or after `synced`, plus new ones, and the About page by its ID in `sync.md`, delete files for pages that are gone, set `synced` to `date -u +%Y-%m-%dT%H:%MZ`, and follow the new versions. Also refresh when the owner says "refresh my hub". No copy yet: build it as **Local copy** in <skill>/backends/notion.md says.
  - Edit the hub in Notion, never only in the copy, then refresh that page. The one exception is guava-bar on a Mac, which switches a head-chef or line-cook line in the copy first and updates Notion right after. Read the Tasks database (its ID is in `sync.md`) only when work needs a task, never at start-up or into the copy.
  - Save what you learn (decisions and their reasons, corrections, preferences, project state) to Notion Memory, never to the hub, and check it before work that depends on past decisions. Follow `notion://docs/memory` and **Notion Memory** in <skill>/backends/notion.md, including "forget", "what do you remember about…" and "pause memory". Memories never override the rules page, and they win over your tool's own memory.
- Model routing: hand work to the head-chef and line-cook slots in guava-stack settings, passing each slot's ID and effort to its tool, re-reading their model lines (the bullet under each label) right before each hand-off (after the check above: `grep -A2 -xE 'head-chef|line-cook' ~/.guava-hub/context.md | grep -E '^(head-chef|line-cook|- )'`). Computer use is line-cook work: browser tools first, in the browser where the owner is already signed in, and its tool's computer tools only for apps outside the browser (if its tool has none, use your own). With none named, do the work yourself.
- If guava-stack settings differ from `~/.guava-hub/checked.md`, or this session runs in the head-chef's own tool on another model, follow **Session checks** in <skill>/SKILL.md before relying on them.
- Search before saying you don't know: Notion Memory first, then the rest of the Notion workspace, including source docs the context page links. When sources disagree, follow the owner's current request, then what they said outright over what was inferred, then the newer decision (a page's edit time alone isn't one). If it still matters, show both and ask.
- New skills: when you make a skill for the owner, or they make or add one in any of their AI tools (such as a Claude or ChatGPT skill), add it to the hub's skills database too, as **Add a skill** in <skill>/backends/notion.md says, so every assistant can use it, and fill in its routine columns if it runs on a timer. Ask before turning it on for external agents and Notion AI.
- Routines: when you set up, change or stop a recurring routine, update that skill's Schedule, Runs on, Scheduler ID (the job's ID and where it lives) and Pre-approved (what the owner said yes to in advance for it, in their words) in the hub's skills database in the same step, and check its routines view first so nothing runs twice. Your own scheduler runs it; the hub only lists it. Write into the routine's prompt that each run sets its skill's Last run to the current date and time when it finishes, and adds no task, so the routines view shows whether it really ran and a run that stopped partway leaves Last run behind. When the owner says "check my routines", follow **Check my routines** in guava-hub/skills/guava-hub/SKILL.md from github.com/romeodiaz/guava-stack.
- Tasks and where things live: file work where the context page's **Where things live** says. Log work in the Tasks database it names when it's a bigger piece the owner is involved in and would track: a project, event or feature, such as preparing for a conference or building a new feature. Skip small changes to the system that the owner only approves, such as new icons, adding, removing or renaming a skill, wording fixes and bug fixes: the commit or PR is their record, and when one belongs to a tracked task, add its link to that task's Links instead. Skip questions and quick lookups too. When the work starts, add a task: Name (the request in the owner's words), Goal (the real goal, what done looks like, what would count as failure), Assistant, and Status In progress. When it ends, set Status (Done, Done with concerns, Blocked or Needs you), Touched and Links, with hand-off notes in the task's page. When work has a task, put its ID (such as TASK-12) at the start of commit subjects and PR titles, in hand-offs, and after the `Decided:` date in any memory it decided. A hub edit made under a task sets Touched to Hub on it, never on the old changelog page, which stays only as an archive; a small hub edit needs no task, since Notion's page history keeps it. No passwords, keys, other people's personal details or clients' confidential information in tasks.
- If the hub can't be reached, say so once and carry on. With no hub yet, the owner can say "set me up".
